# Управление расписанием ККРИТ

Отслеживает PDF на публичном Яндекс Диске, отправляет их в закрытую Telegram-группу операторов, конвертирует через CloudConvert, разбирает XLSX и сохраняет расписание в PostgreSQL. Предоставляет внутренний HTTP API двум ботам-получателям.

> Исторический проект на aiogram 3.0.0b6. Исходный Docker-стек использует Python 3.9, Debian Buster и PostgreSQL 13. Эти версии завершили стандартную поддержку. Перед эксплуатацией требуется обновление зависимостей, контейнеров и проверка в отдельном окружении. Проверка исходников не заменяет проверку развёрнутого бота.

## Проекты в этом репозитории

| Репозиторий | Назначение |
| --- | --- |
| [bot-schedule-control-KKRIT](../bot-schedule-control-KKRIT/) | Загрузка, обработка и внутренний API расписания |
| [bot-schedule-KKRIT](../bot-schedule-KKRIT/) | Расписание для студентов |
| [bot-schedule-KKRIT-teacher](../bot-schedule-KKRIT-teacher/) | Расписание для преподавателей |

Клиенты читают `/hulls`, `/groups`, `/schedules` с `http://schedule-control-KKRIT-bot` в общей Docker-сети `control-KKRIT`. Каждый проект использует собственные PostgreSQL и Redis. Telegram работает через long polling. Сначала подготавливают управляющий проект.

## Конфигурация

Скопируйте `.env.sample` в `.env`. Пример `BOT_TOKEN` фиктивный: для запуска нужен собственный бот, созданный через BotFather. Не запускайте вторую polling-копию с рабочим токеном существующего бота.

| Переменная | Значение |
| --- | --- |
| `BOT_NAME` | Уникальный префикс имён контейнеров |
| `BOT_TOKEN` | Токен отдельного Telegram-бота |
| `ADMIN_ID` | Telegram ID доверенных администраторов, через запятую |
| `POSTGRES_DB`, `POSTGRES_USER` | Имя базы и пользователь |
| `POSTGRES_PASSWORD` | Обязательный уникальный сильный пароль; в примере пустой |
| `DB_HOST`, `DB_PORT` | В Compose: `postgres`, `5432` |
| `DB_OUT_PORT` | Порт PostgreSQL на `127.0.0.1` хоста; не должен конфликтовать с другими проектами |
| `KKRIT_DISK` | Публичная ссылка Яндекс Диска с расписаниями, не OAuth-токен |
| `GROUP_ID` | Числовой ID закрытой группы операторов, обычно начинается с `-100` |

Все участники `GROUP_ID` могут загружать документы и менять справочники. Членство в этой группе является границей доступа; не добавляйте туда недоверенных пользователей.

Для PDF-конвертации создайте локальный файл `data/cloudconvert_api_keys.json`:

```json
{
  "primary": "REPLACE_WITH_YOUR_CLOUDCONVERT_API_KEY"
}
```

Каталог `data/` исключён из Git. Ключи используются с `sandbox=False`; конвертация расходует реальные кредиты. PDF отправляется стороннему сервису CloudConvert.

## Подготовка запуска

Ожидается Linux с Docker Engine и Compose v2. Ниже сохранён способ запуска исторической версии; сборку и интеграции нужно проверить после обновления стека. Не подключайте существующий каталог `pgdata/` к новой major-версии PostgreSQL без миграции.

```sh
cp .env.sample .env
# Заполните .env, задайте уникальные порты и пароль.
docker compose config --quiet
docker compose build
docker compose up -d
docker compose logs -f bot
```

Compose требует непустой `POSTGRES_PASSWORD`. БД и Grafana привязаны к loopback хоста. Внутри общей Docker-сети HTTP API не имеет аутентификации: присоединяйте к ней только доверенные сервисы и не публикуйте порт `80` управляющего бота наружу.

При уже созданном PostgreSQL изменение `.env` не меняет пароль в существующей базе. Ротацию выполняют средствами PostgreSQL и согласованно обновляют конфигурацию клиентов.

Первичная инициализация:

1. Добавьте бота в закрытую группу из `GROUP_ID`.
2. Инициализируйте флаг: `docker compose exec redis redis-cli SET power-schedule 0`.
3. Через `/get_online_hulls` получите JSON и отправьте его после `/update_collect_data_hulls`.
4. Извлеките группы из XLSX через `/get_groups_on_schedule`, затем сохраните JSON через `/update_collect_data_groups`.
5. Отправьте XLSX с датой в имени, выберите корпус, парсер и правило, подтвердите сохранение.
6. Администратор из `ADMIN_ID` включает выдачу через `/power_schedule`.

Имена учебных групп и структура документов зависят от конкретного источника. Парсеры `kr` и `sv` выбираются вручную. Пустые справочники не содержат расписаний сами по себе.

## HTTP API

- `GET /hulls` — словарь корпусов, включая пути публичного диска.
- `GET /groups` — группы по корпусам.
- `GET /schedules?hull=...&date=YYYY-MM-DD&limit=5&sort=asc` — расписания с указанной даты и позже. При выключенном флаге возвращает пустой список; максимальный положительный `limit` — 15.

API читает расписания, не предоставляет доступ к таблицам Telegram-пользователей и не принимает изменения расписания.

## Команды

- /show_collect_data — показать корпуса и группы;
- /get_online_hulls — получить корпуса с Яндекс Диска;
- /update_collect_data_hulls — заменить JSON корпусов;
- /update_collect_data_groups — заменить JSON групп;
- /get_groups_on_schedule — извлечь группы из XLSX;
- /convert — конвертировать PDF в ответном сообщении;
- /power_schedule — включить/выключить выдачу расписания (только `ADMIN_ID`);
- /statistics — статистика, только для `ADMIN_ID`;
- /broadcast — рассылка, только для `ADMIN_ID`.

## Структура и данные

- `app/handlers/` — Telegram-обработчики.
- `app/services/scheduler/` — периодические задачи.
- `app/infrastructure/database/` — модели и SQLAlchemy-запросы. Таблицы создаются через `metadata.create_all`, системы миграций нет.
- `locales/ru.ftl` — русская локализация.
- `data/`, `pgdata/`, `redis_data/`, `grafana-data/` — локальные рабочие данные; не публикуются.

База содержит Telegram ID, имена, usernames и настройки пользователей; логи ошибок могут содержать Telegram updates. Дампы, логи, `.env` и реальные документы расписания не должны попадать в публичный репозиторий. Для демонстраций используйте вымышленные данные.
